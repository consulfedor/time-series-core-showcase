Инженерный кейс / данные и надёжность

Сервис работает.
А данным можно доверять?

В собственном проекте я выстроил путь рыночных данных: получение, хранение, расчёт и проверка истории. Отдельная задача — обнаружить пропуск и восстановить основание для дальнейшей работы.

Задача

Аналитике нужен непрерывный временной ряд. После разрыва соединения или перезапуска хранилище может отвечать, но содержать неполную историю.

Поэтому доступность сервиса, свежесть данных и полнота диапазона проверяются отдельно.

Мой вклад

Архитектура потока, жизненный цикл данных, восстановление, проверки и операторский интерфейс. Разработка ведётся с ИИ-агентами; требования и приёмку я связываю с наблюдаемым результатом.

Предмет кейса — инфраструктура данных. Торговые правила и доходность здесь не демонстрируются.

Путь одной записи

У каждого слоя — своя задача

01 / Источник

WS / REST

Живые события и получение нужного исторического диапазона.

02 / Буфер

Redis

Оперативное окно данных для текущей обработки.

03 / История

MongoDB

Базовые и рассчитанные записи, временные отметки и контроль полноты.

04 / Потребители

Аналитика / ML

Проверенная история, производные наборы и Parquet-снимки.

Проверка источника и качества связывает эти этапы. Наличие записи ещё не означает, что она пригодна для последующего расчёта.

Объект результата

Диапазон данных с известным происхождением, проверкой полноты и состоянием производных расчётов. Рядом — отчёт, по которому можно продолжить работу или разобраться в сбое.
