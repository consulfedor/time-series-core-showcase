0. Human and AI work as a whole

The person defines the goal and accepts the result. Oz coordinates agent actions, while the Harness connects memory, models, tools and working rules. The person accesses a document, dataset or task state through the interface; the agent uses APIs and tools to access the same version and supporting material.

Goal → plan → actions with oversight → checks → accepted result → retained experience.

Oversight continues throughout the work: the contributor, next step, deviations and decisions needed remain visible. Checks assess the result; the person decides whether to accept it. Retained evidence helps resume a task after a break and apply reviewed experience to subsequent work.

Conversation, attention and continuity

A draft, a queued message and a sent message are distinct states. History and search lead back to the task. Delivery is checked against the same message, rather than inferred from text disappearing from the input field.

The history retains tasks and decisions. The plan shows the next step, dependencies and result; bookmarks identify relevant passages in a long conversation. The model and reasoning settings concern execution, while documents and checks belong to the task itself.

Contributor states distinguish work in progress, a pending decision and completion. After a break, the goal, materials and result state are recovered first. Before repeating an external operation, its previous execution is checked.

Access, voice and sound

The web interface opens the conversation and materials; the server-side terminal session has a separate lifecycle. Mobile and remote access use their designated routes. A client application and browser are separate interfaces whose capabilities may differ.

A sound notification draws attention to the state of work. Browser text-to-speech reads a selected translation. These are separate actions; neither establishes voice input or two-way conversation. Microphone, dictation and conversation support depend on the particular client and are checked separately from text chat.

Client or channel Actual interaction path Capability boundary
UI5175 in the browser Conversation, materials and the associated server terminal, with a responsive view for narrow screens. The browser is not the agent's execution process.
UI5175 sound A work-state sound through the notification controller. Attracts attention; does not record speech.
Translation read-aloud The selected text is sent to the browser's speechSynthesis interface. Reads text aloud; available voices are determined by the browser.
Voice input and conversation An integrated microphone conversation is not part of the UI5175 interface shown here. External client features are not presented as the Harness's own implementation.
Transcription and audio files A transcript is treated as a document; audio is handled by a suitable tool. Recording requires separate consent, access and retention rules.
Web, Desktop App and Codex Distinct clients for working with the server and its tools. Connecting one client does not establish another client's authorization or voice capabilities.

Results in different formats

A file on disk, processing by a dedicated tool and an embedded preview are different capabilities. Explorer helps locate the material; its format and purpose determine how it is opened.

Material Processing and source Viewing and sharing
Tables and data The dataset, schema, units and calculation. A table view or dedicated application; the source file is retained.
Markdown Authored text and its version. A Reader with a table of contents; the source is available separately from the presentation.
HTML and SVG A document, interactive example or diagram. HTML opens in an isolated viewer; SVG requires a suitable viewing method.
DOCX and PDF An editable document and its print edition. PDF opens in a PDF viewer; a DOCX file does not imply an embedded Word editor.
CAD A drawing or model, exchange format, dimensions and geometry. A dedicated tool or viewer; an image does not replace the source model.
Images The original, its provenance and connection to the task. An image that can be enlarged; a screenshot shows the view but does not replace the data.
Audio A recording or transcript with authorized access and retention conditions. Playback and text processing depend on the client and tool.

The version, owner and storage location connect the file to the task. Changes retain history; archiving and deletion account for active consumers of the result. The shared lifecycle is explained under operations and preservation, and verification under quality.

Freshness, contradictions and replacement

When sources conflict, their dates, applicability and owners' decisions are compared. A newer note does not overrule a current rule merely because it is newer. Replacement records what changed and why.

Outdated material is excluded from active context but may remain in history to reconstruct a decision. Archiving and deletion account for retention periods and consumers: a source reference must not silently disappear from a result that depends on it.

An example: read-only access

'Let the agent read the data, but do not allow changes.'

  1. Find the concept. The thesaurus connects words such as 'connection', 'access' and connection to the relevant subject and its terminology.
  2. Understand the boundaries. The wiki and ontology distinguish a secret, a connection and an authorized action.
  3. Establish the rule. The connection document defines the purpose, consumer and allowed operations. Related experience helps account for past mistakes.
  4. Perform the action. An authorized tool uses the connection through the security layer and returns the result.
  5. Verify together. The person in the UI and the agent through the API check the result of the same operation on the same connection. Useful experience is reviewed before entering shared knowledge.

This illustrates relationships between layers, not a mandatory automated route for every request. Finding a note does not grant access or replace the current contract.

Working example and explanation ↓

The goal defines the work boundaries

First define the result: what must be produced, from which materials and under which acceptance conditions. The plan connects that result to steps, contributors and dependencies. Completed actions are evaluated against the goal, not in isolation.

Priority changes the order of ready work. It does not remove result checks or permit losing another contributor's unfinished changes.

Attention and the next step

The current goal, next step, responsible contributor and any decision needed from the person remain in focus. A required dependency is resolved to achieve that result; an adjacent improvement is recorded separately rather than replacing the assignment.

After a break, accepted decisions, materials and the actual execution state are restored. Compaction reduces the history that must be reread while retaining the goal, its basis and unresolved questions.

Contributors and responsibility

A persistent agent maintains a long-running workstream and has a profile: purpose, role, session association and chosen execution mode. A team brings participants together around a task. Its members and lead are visible to the person.

The orchestrator owns the combined result: analyzes the task, identifies dependencies, assigns independent parts, checks returned material and brings the work to completion. It can also perform part of the work itself.

HumanGoal and criteria→ OrchestratorPlan and dependencies→ ExecutorsRoles and tools→ Combined resultVerification and acceptance

Temporary helpers can perform bounded, independent checks:

  • code_mapper — ownership, entry points, invariants and impact;
  • docs_researcher — canonical documents and version-sensitive behavior;
  • browser_debugger — DOM, console, network and screenshot evidence;
  • reviewer — advisory review of a frozen diff, without authority to issue the final PASS.

A temporary helper returns its result to the assigning agent. A persistent role, session, team membership and specific task remain distinct. Team membership alone does not establish availability or task completion.

Parallel preparation and a combined result

Independent parts can be prepared concurrently in separate working copies. Ready changes enter a shared service through coordinated integration: checking the current version, the preceding contributor's result and compatibility. The combined user scenario is verified after integration.

Translation depends on an agreed source text; publication depends on a verified set of files. Fact collection and analysis of independent materials can run in parallel. Dependencies determine the order, rather than a desire to keep every contributor busy at once.

A web agent or CLI orchestrator may manage the plan. Handoffs preserve the task, criteria, authority and unfinished actions. A manual pilot, agreed roles and automated management require separate maturity checks.

What is visible without revealing a key

The record contains a purpose, account and environment, consumers, permitted operations, configuration status and checks. Storage availability, credential suitability and a successful business operation are assessed separately. For example, verifying an account does not establish permission to download any restricted resource or make an unauthorized change.

A trusted application receives only the fields it needs. It can read its own credentials to perform the work; the agent receives the result and permitted metadata. Delivery methods suit the application, including service credentials and environment adapters, without distributing a shared bundle to every process.

Replacement, revocation and sensitive data

Credential replacement has a revision and a list of consumers. Use of the new revision is checked afterwards; revocation must stop the relevant action. Audit records connect the operation, result and time without placing secret values in the conversation, screenshots or public files.

Connection secrets and document contents are protected separately. Permitted material and the processing route—an external provider or compatible local inference—are defined before sending data to a model. A summary must not disclose more than the original action allows.

Scope of protection: keeping a key out of the response does not replace permission checks and controls on returned data. Storage on a shared host does not isolate the value from an administrator with full privileges. Compatibility, access recovery and revocation are checked for each consumer.

Working example and explanation ↓

Research connects a question, data, experimental conditions and a testable conclusion. WebSocket/REST ingestion, processing, Redis/MongoDB and Parquet prepare the time series. Historical completeness and freshness are checked separately from service availability. The scheduled export provides a specific, dated result of preparing that input.

From a hypothesis to a conclusion

Step Evidence retained
Question What is being compared and which result would refute the hypothesis.
Data The period, schema, features, provenance and known limitations.
Experiment The method, parameters, fixed split and comparison baseline.
Evaluation Training results separated from results in the next time period; errors by class.
Replication The same configuration and inputs allow reproducibility to be checked.
Conclusion Accepting, rejecting or refining the hypothesis, with supporting evidence.

The research record dated 6 October 2026 retains run conditions, feature sets and confusion matrices. Two independent repeat fits of one preselected configuration checked determinism. Repeatability was not treated as evidence of predictive quality, and this test was not used to select a new best model.

Training, evaluation and application

The dataset, training, calibration, evaluation and inference have separate results. For a time series, the evaluation period follows the available training data. Strong performance on previously studied data does not establish transfer to the next month; tuning against an already inspected test changes what the evaluation means.

The project has used Python, PyCaret, LightGBM, MLflow and Model Lab for the relevant analysis and experiment-tracking stages. The hypothesis determines the tool; a model is unnecessary where a calculation is sufficient.

The chart leads to an event, its data and calculation conditions. The journal retains the automated candidate separately from the person's decision. A negative result also has value: it limits the hypothesis instead of repeating an unsuccessful experiment under a new name.

Applied example: DORI

The package includes DORI Camera Selector / Designer — a standalone single-file HTML tool built as a separate practical example using an agent workflow.

It has two modes:

  • Direct Calculator: equipment → calculated result;
  • Designer: task and geometry → equipment requirements.

The example demonstrates a complete small implementation cycle:

  1. Task and inputs: a domain need, parameters and constraints.
  2. Calculation: the engine and SVG geometry visualization.
  3. Selection: DORI / PPM as the basis for the decision.
  4. Result: a standalone interactive HTML artifact.

The tool accounts for resolution, sensor size, focal length, mounting height, tilt, target distance, blind zone and installation geometry. It shows how a concrete request can become a working interface with calculations and a visual explanation of the result.

DORI is not part of MyTwoBrain's private core. It is included as an independent implementation example.
