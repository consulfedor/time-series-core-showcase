    03 · data

    From source to result

    Every conclusion has supporting evidence: a document, a data version and a reproducible calculation.

    Three processing stages

    01 · ingest

    Preserve the original fact

    Connectors ingest documents, ERP records, spreadsheets and CAD/BIM. The registry records the owner, version, time and access rights.

    Result: the source can be found and checked.

    02 · verify

    Link data to the object

    Checks identify duplicates and contradictions. Facts are matched to the object, work item, period and units of measure.

    Result: consistent context for calculation.

    03 · prepare

    Calculate and explain

    SQL, formulas and engineering tools calculate metrics. The model explains them within the permitted context; the harness checks the output.

    Result: evidence-backed material for a decision.

    What stays with the conclusion

    ProvenanceThe precise source fragment, its owner, revision and checksum.
    Time and transformationsWhen the fact applied, when it arrived and which rules processed it.
    Verification and historyThe calculation, identified gaps, verification result and the responsible person's decision.

    Source changes → the previous result is marked stale → related calculations and checks run again.

    06 · teamwork

    From task definition to acceptance

    A person defines the goal and makes the decision. Agents prepare the result; the orchestrator connects executors, dependencies and checks.

    Who is responsible for what

    Process owner

    Goal and acceptance

    Defines the useful result, constraints and criteria. Resolves domain questions and accepts the work.

    Agents

    Preparation and execution

    Clarify the specification, gather context and perform permitted tasks. Preserve evidence and the result of each step.

    Orchestrator

    Dependencies and sequence

    Distributes independent tasks and tracks dependencies and readiness. Coordinates publication in the agreed order.

    Six steps for one task

    1. Task definitionWhat needs to change and who needs the result.
    2. SpecificationBoundaries, examples, unknowns and acceptance criteria.
    3. ExecutionAgents work with the same context version.
    4. VerificationTests and domain review verify the result.
    5. DeliveryThe verified version is published with a rollback path.
    6. FeedbackImpact, errors and new conditions feed back into the task.

    The engineering foundation is MyTwoBrain, a custom harness around CodexCLI: dialogue, roles, tasks, tools, checks and history. Other models and environments connect through verifiable adapters. Permissions, integrations and recovery are validated in the company's environment.

    07 · verification and trust

    Agent verification and authority

    Authority increases after a scenario has been verified. A completed answer, a verified result and a human decision are recorded separately.

    Levels of access

    1. L0 · Interface onlyThe system provides no agent entry point.
    2. L1 · API and CLITyped operations and defined permissions are available.
    3. L2 · Controlled read accessInitial pilot: the agent reads permitted data and prepares material.
    4. L3 · Recommendations and actionsChecks, preview, approval and an execution receipt.
    5. L4 · Operation at scaleShared policies, an agent portfolio, cost and incident controls.

    Three measures of the result

    TimeTime from task definition to acceptance; waiting, blockers and rework measured separately.
    QualityVerified evidence, defects, security and reproducible calculations.
    CostModel, infrastructure and human time costs per accepted result.
    Connections tied to purpose. The user supplies a secret; the registry shows its alias, purpose and validation status. A trusted executor receives the permitted operation. The agent receives the result and a receipt, without the key itself.

    C1 vision: the Fact → Decision system
    

    Local corporate environment for construction management intelligence
    

    Status: an architectural proposal for agreeing on goals and preparing an implementation plan.
    

    Fedor · independent C1 version 1.5 · 6 October 2026.
    

    This document defines the system to build, its business value and the path from C1 to specific work packages. It also identifies the data needed to choose the architecture, models, software harness and hardware on a defensible basis.
    

    Working name
    

    Short name: Fact → Decision system.
    

    Formal name: a local corporate environment for evidence-backed management intelligence.
    

    The proposal covers development and deployment for construction and design companies, contractors and technical clients. Initial discussions involve a project, construction engineering, document-control or procurement manager together with the data owner. The common architecture and engineering procedures are reusable; each company's processes, connections, permissions and rules are configured separately.
    

    The system ingests scattered corporate data, preserves its provenance and freshness, then checks, normalizes and links facts. It performs calculations and local model inference to produce information that management can use.
    

    A defining property is traceability back from a conclusion: a management-level abstraction can be opened to its supporting fact, document, accounting record, calculation or drawing element, within the user's permissions.
    

    People use the system through a shared workspace for people and AI: a clear interface linking questions to tasks, documents, plans and verified results. Agents access the same objects through permitted APIs and tools. A manager can clarify intent, see progress, check evidence and decide without manually assembling context from separate systems.
    

    Tools that make the decision object visible
    

    A manager opens a construction area and sees its drawing, 3D model, quantities, schedule, deliveries and documents. Selecting a pour section in one view opens its evidence in the others. An agent finds a discrepancy, verifies the calculation and prepares an instruction with an assignee and deadline.

    C1 goals
    

    

    Develop an evidence-backed vision and target architecture for a construction company's local AI environment. It turns scattered documents, accounting data, drawings and engineering and operational information into connected corporate memory, then uses it to form traceable, high-level management abstractions. People and agents work with these through a common observation and interaction point, from defining the question to checking evidence and making a decision.
    

    

    The business goal in one sentence:
    

    

    Shorten the path from a corporate fact to management understanding and a decision.
    

    

    C1 is the top-level business abstraction. It answers: why the system is needed, what the company receives and which boundaries must hold. Specific models, databases and servers are selected at lower levels based on tasks, data, workload and acceptance criteria.
    

    C1 architectural invariants
    

    These rules hold regardless of the chosen models, harness, storage or hardware.
    

    






    
Invariant
Meaning for the system

    
    


    
Corporate sources retain their authority
SAP, CDE/BIM, file stores and other operational systems remain the SSoT for their facts; the system builds verifiable projections and does not replace data owners

    

    
Evidence before conclusions
Every material claim links to the original object, version, precise fragment, time, permissions and transformation chain

    

    
Metrics are calculated deterministically
Totals, quantities, percentages, dates and statuses come from approved formulas, rules and calculation tools; the model explains and connects the results

    

    
People and agents observe the same working object
UI and API use the same data owner: identifier, revision, freshness and evidence agree within each party's permissions; discrepancies remain visible rather than being hidden behind a common 'done' status

    

    
User identity follows the complete path
Role, project and access constraints apply to search, calculation, tool calls, inference and result publication

    

    
Only the local environment processes real data
External frontier models can accelerate development of the platform, UI, harness, modules and adapters using schemas, contracts, public and synthetic data only; corporate documents, databases, indexes, logs, user requests and responses are unavailable to them

    

    
The harness enforces security, not the system prompt
The prompt defines model behavior but grants no authority; IAM/ACL and policies authorize data and tool access before context retrieval, and the result is checked again before publication

    

    
Derived layers are rebuildable
The graph, full-text and vector indexes, OCR text, translations and summaries can be rebuilt from authoritative sources and the evidence log

    

    
Memory types are separated
Evidence, corporate semantics, search indexes, shared project context, processing state and personal context have different authority and lifecycles

    

    
Ontology precedes the graph database choice
Types, identifiers, relationships, units and constraints form a versioned domain contract; a graph database is one possible projection

    

    
BIM and CAD remain native engineering domains
Preserve the source model, revision, GUID, spatial structure, properties, coordinates and specialist verification results, not just text or an image

    

    
The first slice is read-only
Changes to a corporate system are allowed later only through typed actions, preview, policy checks, approval and execution receipts

    

    
Logical modularity with physical simplicity
Responsibility boundaries and contracts are defined early; components are physically separated when measured workload and operational needs justify it

    

    
Models and products are replaceable
Stable data, evidence, tool and result contracts do not depend on a specific LLM, database, framework or interface

    

    
Replication through configuration
The common core, domain packages and tests are separate from local data, connections, permissions, site rules and model profiles

    Target design: two environments
    

    Shared-platform development is separate from operations on protected real data. External frontier models in an authorized build plane can help design and build the harness, UI, processing pipelines, plugins, skills, MCP/APIs, tests and model adapters quickly and well. Without additional security approval, they use only platform code, schemas, contracts, public material and synthetic datasets.
    

    Protected user requests, PII, commercially sensitive and other restricted corporate data are processed by local models within the on-premises environment. Local models do not connect directly to sources: the harness supplies minimum permitted context and tools through a local model gateway.
    

    The architecture allows a separate policy-gated route to a frontier model only for an explicitly permitted data class: public, synthetic or demonstrably minimized and de-identified. This route is disabled by default. It requires approved security/legal policy, provider retention and training terms, DLP checks, quotas, logging and negative evals. Approval applies to specific data, operations and providers, not automatically to the entire project. Source code is classified too: a confidential implementation does not become public simply because it contains no user documents.
    

    AI4SDLC as the C1 operating model
    

    Here, AI4SDLC means redesigning the complete cycle, rather than adding a separate AI feature: intent → specification → agent execution → evidence → release decision → observation of results. As coding accelerates, the bottleneck shifts to choosing goals, coherent context, specification quality and result verification. C1 therefore centers on a small team's ability to take an important scenario from a problem to a measured effect reliably, rather than on agent counts or generated lines of code.

    Agentic SDLC and the task-definition contract
    

    One owner carries an end-to-end scenario from business problem to proven result. Analysis, development, QA, security and operations roles do not disappear: their expertise becomes explicit rules, reusable capabilities, automated checks, human gates and specialist consultations at risky boundaries. Greenfield work can start with an agent-first process; brownfield work first needs reverse engineering, owners, contracts and characterization tests.
    

    The company's process owner maintains the goal, domain meaning, real examples and decisions that cannot be derived automatically. The agent organizes context into levels C1 → C5, separates facts from hypotheses, exposes contradictions and produces a versioned specification. SDD does not require the operator to write a perfect formal document: the agent must turn a coherent explanation into a compact human-agent contract, covering intent, boundaries, data, examples, unknowns, non-goals and acceptance criteria, then return it to the person for a meaning check before implementation.
    

    Agent work has three complementary modes: an editor alongside a person, terminal execution of a bounded package, and background/remote work followed by a receipt. The last matters especially for a small team: people need not watch every intermediate step, but must receive questions, changes, evidence, cost and uncertainty at decision points. Otherwise, human attention becomes the new bottleneck and a faster agent does not speed up the overall flow.
    

    A poor specification scales errors, so subsequent messages are treated as changes to one context package, not independent requests. A requirement change triggers impact analysis across architecture, tests, evals and existing results.
    


    Coordinating people and agents
    

    A person defines the result and accepting party. The orchestrator breaks the goal into bounded packages, assigns owners, tracks dependencies and raises questions requiring decisions. A durable agent maintains its working context; a temporary subagent receives a narrow assignment and returns its result to the owner.
    

    Independent reading, analysis and preparation run in parallel. Coordination is required when changing a shared source or publishing a result, not before every operation. Responsibility transfers only after the receiving owner confirms. Task history preserves the goal, constraints, last accepted version and exact next step after interruption.
    

    The common observer shows people and agents the same object: task definition, executor, state, evidence and result. A configured role, available terminal or notification is distinct from actual execution and an accepted result. Describing a role in a profile grants no technical authority; the executable access layer checks it. 
    

    An agent-first platform separates three infrastructure layers. The model gateway routes internal and external models, budgets and data policy. The tool/MCP gateway authenticates and constrains calls. The capability registry describes useful operations, their owners, permissions, inputs, outputs, maturity, SLOs and evals. The GUI gives people access to task definition, collaboration, settings, investigations and approvals. Agents access the same objects through APIs and capabilities; the platform enforces domain rules, state changes, limits and effect boundaries regardless of interface.
    

    Project-scoped execution profile — open direction
    

    A separate versioned execution profile can define each project's permitted plugins, tools, agents, models, memory, policies, limits and credential references. One base runtime can then serve different projects without mixing capabilities, permissions or context. Dynamic profile changes need separate validation; in production, every change requires a versioned diff, policy preflight, state-compatibility checks, rollback and a receipt.
    

    Secrets and capability security
    

    Secrets management and harness security are related but different. The C1 principle is: credentials are issued to a permitted action, not to a model, prompt or unrestricted agent. Target path: user/service identity → policy engine / capability broker → typed tool call → scoped short-lived credential → API, after which the agent receives only the permitted result and a receipt. This reduces the consequences of prompt injection, context leakage and compromise of one project.
    

    Project and agent identities, least privilege, dynamic/short-lived credentials, rotation, revocation, audit and project isolation belong in the mandatory security backlog. Credential storage and issuance technology is selected at a lower level after threat modeling and assessment of infrastructure constraints and security requirements. Secrets do not enter specifications, prompts, logs or agent memory, and are not stored in the repository as plaintext.
    


    A connection as a business capability
    

    The user and agent agree on a clear connection alias, purpose, owner, permitted operations, project and consumers. The user enters the secret through a protected form. A metadata registry shows whether it is configured, when and how it was tested, whether it works, its expiry and required corrections. Value presence, a successful access test and successful execution of an operation are distinct statuses.
    

    The agent uses an alias and a typed capability, such as 'get the approved quantity schedule', rather than 'read the key from the environment'. The gateway checks identity, resource, action and limits; a trusted executor receives the credential, while the agent receives the permitted result and receipt. Services and containers get only their own connections, without copying shared secrets into .env for every process.
    

    Short-lived credentials are used where the source supports them; permanent keys stay in a protected backend with restricted access and revocation. UI and API use the same metadata/status registry, but reading it reveals no secret values. This design constrains ordinary users and agent processes; protection against a host administrator requires a separate threat model.

    Engineering basis of the proposal
    

    The existing MyTwoBrain environment connects a knowledge base, agent roles and groups, dialogues, work packages, tools, checks and an operator interface. This architecture describes the target construction system; it is not presented as an already operational industry case.

A derived projection tied to its source version; translation does not become a new fact owner

    

    
Result and decision
Conclusion, calculation, evidence, limitations and required approval
Saved artifact, verification receipt and a separately recorded human decision

    
    

    

    The working loop closes: a person asks → the agent clarifies the task and performs permitted work → both see the result and evidence → the person decides → the decision updates the plan and next-step context. Independent reading and preparation do not require approval at every step. Questions return to the person when domain judgment, authority or consent to a change is needed.
    

    For example, a manager asks: 'Why does completed work differ from the plan?' The agent finds permitted sources and calls a calculation tool. In the same workspace, the manager sees the summary, plan/document revisions, discrepancies and links to calculation rows. A clarification becomes a recorded task change; the accepted result retains its evidence.
    

    Verifiable results depend on the common observer point together with execution contracts. A deterministic metric repeats with the same input and rule versions. Model text remains probabilistic and requires domain review; the interface alone does not guarantee truth or repeatability. UI/API disagreement or stale data produces a visible conflict, not a supposedly verified result. Model-answer completion, background-job completion, delivery, verification and human acceptance are distinct events.
    

    The first pilot tests the complete user journey, from a question in dialogue to evidence and a decision. The person must see source version/freshness, open the relevant fragment, refine the task and resume after interruption. The agent verifies the same task, artifact and revision identities through the API; negative tests cover stale projections and access outside the role.

    Execution control in the harness
    

    The harness must provide:
    

      

    • one human entry point and agent access to the same tasks, plans, documents, evidence and results with consistent identifiers and versions;
      • 

    • request authentication and end-to-end preservation of user, role, project, purpose and session identity;
      • 

    • IAM/ACL and domain-policy checks before search, document retrieval, calculation or tool calls;
      • 

    • task routing across search, calculation, CAD tools, translation, models and approval;
      • 

    • retrieval of only the minimum required permitted documents and data fragments;
      • 

    • local model calls through one local model gateway, with no cloud fallback for protected requests;
      • 

    • tools connected through a versioned allowlist of plugins, skills, MCP and APIs with least privilege; initially read-only;
      • 

    • separation of system instructions from user input and document content, prompt-injection protection, and no model-driven expansion of context or authority;
      • 

    • isolation of users, projects, sessions, memory types and caches;
      • 

    • schema, required-field, evidence-link and ACL checks, plus DLP leakage checks before result publication;
      • 

    • retention of the sources, tools, models and versions used;
      • 

    • redaction of sensitive log/telemetry fields, with access and retention limits;
      • 

    • controlled retries, timeouts, queues and partial-failure recovery;
      • 

    • mandatory approval for actions changing corporate systems;
      • 

    • reference quality, latency and resilience checks after every update.
      • 

    

    The system prompt defines the task, response format, evidence-handling procedure and disclosure restrictions. It is useful as a behavioral layer, but it is not an authorization mechanism: the model receives neither source credentials nor direct database, filesystem, network or tool access, and cannot grant itself these rights. Every proposed tool call is separately allowed or rejected by the harness.
    

    The technical direction separates orchestration logic from long-term memory. Approaches in the Hermes family can serve as the harness, while approaches in the OpenViking family can provide file and context memory. Specific components follow comparative testing on target scenarios.

    Protection rests on technically enforced boundaries, not a model's promise to withhold information. The external build plane creates the shared software system without corporate-data access. The local data plane handles real user requests, applies corporate authority and calls local models only.

    Corporate-system action boundary
    

    The first vertical slice reads sources and produces evidence-backed results. Production-write authority stays disabled until read scenarios, evidence and access separation pass separate acceptance.
    

    A later modifying scenario is a typed action containing the user, target system/object, proposed diff, evidence references, preconditions, access-policy decision, required approvals and idempotency key. The system previews the result before execution. Afterwards, it saves a receipt, reads the source again and compares actual changes with the agreed action.
